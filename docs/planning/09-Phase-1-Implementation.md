## Database design (proposed physical names, not production SQL)
Use separate creator-prefixed tables (`acc_` prefix and the `acc_private` schema) inside the existing Almost Heard Supabase project. Creators does not get a second database. UUID PKs, timestamptz UTC, created_at/updated_at, audit actor IDs on mutations, deleted_at for catalogue soft deletion. All tenant tables carry non-null creator_id and unique (creator_id,id) for composite FKs. No client-assigned owner changes. No anonymous access in foundation.
 
| Table | Fields and constraints |
|---|---|
| acc_creators | id UUID, auth_user_id UUID unique FK auth.users, display_name text, handle text nullable until public naming policy, membership_state text server-controlled (active/inactive/cancelled proposed internal representation), cancelled_at, retention_until; timestamps |
| acc_storage_connections | creator_id unique FK, account identifier, bucket configuration, public_base_url nullable, encrypted access key and secret (ciphertext, nonce, key version), health status, checked_at; credentials inaccessible to client roles |
| acc_artists | creator_id, id, slug, name, bio nullable, artist_kind individual/band, distrokid_distributed boolean, visibility, sort_order, audit fields; unique tenant slug. Every artist is an independent catalogue entity. There is no band roster, member link, or Canon relationship. `standalone_artist` was removed by `20261127200000_acc_drop_standalone_artist.sql`, which is applied. |
| acc_releases | creator_id, id, slug, title, description nullable, primary_artist_id composite FK, release_type, release_date nullable, distrokid_distributed, visibility, published_at, sort_order, audit fields; unique tenant slug |
| acc_songs | creator_id, id, slug, title, description nullable, primary_artist_id composite FK, duration_ms nonnegative nullable, recording_kind nullable, distrokid_distributed, visibility, published_at, sort_order, audit fields; unique tenant slug. Genres are omitted until Creators can reuse the website genre catalogue (see 04). |
| acc_recordings | creator_id, id, song_id composite FK, version positive integer assigned by the database, is_current boolean, first_published_at nullable, retired_at nullable, checksum_sha256, duration_ms nullable until that recording is current, audit fields; unique song/version, partial unique current per song |
| acc_release_tracks | creator_id, id, release_id composite FK, song_id composite FK nullable, placeholder_title nullable, disc_number and track_number positive; exactly one song or nonblank placeholder; unique release/disc/track and unique release/song when song nonnull |
| acc_media | creator_id, id, artist_id/release_id/song_id/recording_id nullable composite FKs, kind cover/audio, bucket, object_key, byte_size positive, mime_type, checksum_sha256, etag, revision, verification_state, verified_at, current flag; exactly one parent; audio only recording, cover only artist/release/song; one current cover per parent and one verified audio per recording; unique bucket/key per connection |
| acc_upload_intents | creator_id, id, target entity reference with ownership validation, server-derived object key, expected type/size/checksum, 15-minute expiry, state, idempotency key; authenticated clients call `acc_create_upload_intent` and cannot insert the table directly; unique creator/idempotency key |
| acc_publication_events | creator_id, id, recording_id composite FK, occurred_at, event kind, idempotency key; append-only; first publication/replacement accounting cannot be erased by deleting song |
| acc_audit_events | creator_id, id, actor, action, entity type/id, timestamp, sanitized details; append-only, no secrets |
 
Relationship: creator 1:N artists/releases/songs; artist 1:N songs/releases; release N:M songs via ordered tracks; song 1:N submission rows in acc_recordings, with one current audio file; a retired submission is not playable; each catalogue entity 0:1 current cover. Keep song identity for editing/grouping but future playback/favourites use recording ID, never silently resolve retired ID to current. Use composite FKs on all relations, including joins. Restrict hard deletion of referenced entities; remove track association without deleting song. Preserve publication history. Add indexes on creator_id + visibility/deleted_at, creator_id + artist, track order, current recording, publication event timestamp. Featured credits, band roster and external link details require owner scope confirmation; do not import Canon data or invent cross-tenant collaboration. Existing release type source contains album/ep/single/compilation/hatty; owner must confirm guest options (recent product direction differs). No rigid guest enum until confirmed; use established types in isolated fixtures only.

## Auth and access
Supabase SSR cookie sessions, verified server-side user on each request; refresh middleware is convenience, not authorization. Register/login/logout/password reset and email verification using Supabase supported flows. Activation/invite policy is an owner gate; do not grant active membership merely from signup. Create creator profile idempotently after verified identity. No shared admin role or service-role client in browser. Active creator may read/write own drafts and storage configuration via guarded actions; inactive/cancelled owner reads retained metadata only, no media preview/private access or writes. Anonymous and other tenants denied. Server-only trusted lifecycle transitions; RLS USING and WITH CHECK ownership and membership, deny ownership reassignment and direct writes to protected state/ledger/credentials. Use narrow RPCs for privileged operations, fixed search_path, revoke PUBLIC execute, validate auth.uid and tenant, never trust client claims. Do not rely on service-role bypass for ordinary CRUD. Cancellation immediately disables private access; 60-day read-only metadata retention, no automated destructive cleanup until retention implementation reviewed. Reactivation payment rule documented in 02; billing deferred.

## Storage and security
Creator owns R2, no platform media proxy. Use bucket-scoped S3 credentials, server-side authenticated encryption with key version and environment-managed master key; no plaintext logs, client payloads or DB exports. Validate account ID and construct R2 S3 endpoint server-side, never arbitrary signing host. Validate HTTPS public base URL and prevent SSRF (reject private/reserved addresses and redirects, use allowlisted verification mechanism). Credential test uses isolated random test key and cleans only that key. Object paths and onboarding are decided in `docs/implementation/STORAGE-ARCHITECTURE.md`: `artists/{artistId}/{uploadId}.webp`, `releases/{releaseId}/{uploadId}.webp`, `songs/{songId}/{uploadId}.webp`, and `songs/{songId}/{submissionId}.mp3` in the creator's own Standard bucket. The app stores each artwork upload as a new object and deletes the previous audio after a successful replacement. The database change is not applied to the shared project yet. Stable IDs not mutable slugs. Recording-specific path reconciles deterministic audio.mp3 with immutable recording identity. Use private-only storage in foundation; never assume prefix hides objects on public R2 custom domain. Public delivery design gate: private bucket plus public bucket or fail-closed prefix gate with alternate endpoints disabled, verified by actual GET/HEAD tests. Originals signed GET/PUT and immutable audio patterns are references, not proof of creator bucket security.
 
Upload: authorize owner/active status, create expiring intent and server-generated key, issue short-lived presigned PUT scoped to key/type, browser uploads direct, finalize server-side checks ownership, expiry, HEAD size/type and content verification; ETag alone is not SHA-256. Verify actual WebP/MP3 bytes and checksum via bounded processing, not browser declaration; if Worker limits prevent verification, fail closed and document staging design. Convert cover to WebP, preview, progress, retry. Use staging keys to avoid overwriting active objects; promote only verified content, reconcile DB/R2 non-atomic failures with durable intent and idempotent cleanup; never delete current good object on failed replacement. Artwork revision query for cache busting. Audio replacement after publication requires warning and explicit confirmation, new recording ID, reset metrics/publication date/eligibility, revoke promotion, consume quota; no remaster exception. Preserve old ID history, do not substitute in playlists. Out-of-band checksum mismatch marks unhealthy and blocks affected publication; future promotion suspension. Health checks bounded, no per-item HEAD on catalogue list. CORS restrict exact dashboard origins and required methods/headers; verify Range 206 for preview; signed GET no-store. No public URLs for drafts. Public URL revocation cannot recall downloaded bytes; later withdrawal must handle origin removal and exact cache purge.
